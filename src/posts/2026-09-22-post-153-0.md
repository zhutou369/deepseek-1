## 遺留代碼重構的困境與 DeepSeek 的角色

遺留代碼的重構之所以難度重重，核心挑戰在於其錯綜複雜的依賴關係和隱晦的業務邏輯。一個「巨石」應用或一個「上帝對象/函式」可能將多個不相關的職責混雜在一起，牽一髮而動全身。手動解耦不僅考驗開發者的經驗和耐心，更需要投入大量的時間進行逆向工程。

DeepSeek AI 在此過程中扮演著強大的輔助角色。憑藉其強大的語義理解能力和代碼生成能力，DeepSeek 可以：

1.  **快速理解代碼意圖：** 將複雜的代碼片段輸入給 DeepSeek，要求它解釋其功能、輸入輸出、副作用及依賴。
2.  **識別潛在模塊邊界：** 協助分析代碼中的不同職責，指出可獨立抽象為模塊的部分。
3.  **設計新的接口與結構：** 根據重構目標，提供模塊的API設計、數據流動建議。
4.  **生成重構後的代碼片段：** 在獲得重構規劃後，DeepSeek 能輔助生成目標模塊的初始實現。
5.  **輔助生成測試用例：** 為重構後的模塊生成單元測試，確保重構過程不引入新的缺陷。

利用 DeepSeek，開發團隊得以更高效地處理遺留代碼的理解與規劃階段，將精力集中於核心業務邏輯的驗證與整合。

### 階段一：遺留代碼分析與問題定義

這是重構的第一步，目標是深入理解現有代碼的內部機制。

#### 提示詞範例 1：代碼功能理解與依賴分析

當遇到一個冗長且邏輯交織的函式時，你可以要求 DeepSeek 像一位經驗豐富的架構師一樣，剖析其職責。

```
提示詞：
「我正在分析一段遺留的 Python 函式，它似乎處理了多種業務邏輯。請你詳細解釋這個 `process_order_legacy` 函式的核心功能、所有輸入參數的意義、可能的輸出結果、它依賴的外部系統或數據（例如數據庫、其他服務），以及其潛在的副作用。同時，請指出函式內部哪些部分負責了不同的職責，並評估其耦合度。

函式代碼如下：
```python
def process_order_legacy(order_id, items, user_id, payment_info):
    # 1. Fetch user data
    user_data = db.fetch_user(user_id)
    if not user_data or user_data.is_suspended:
        logger.error(f"User {user_id} not found or suspended.")
        return {"status": "error", "message": "Invalid user"}

    # 2. Validate items and calculate total
    total_amount = 0
    validated_items = []
    for item in items:
        product = inventory_service.get_product_info(item['product_id'])
        if not product or product.stock < item['quantity']:
            logger.warning(f"Item {item['product_id']} out of stock or invalid quantity.")
            return {"status": "error", "message": f"Item {item['product_id']} unavailable"}
        total_amount += product.price * item['quantity']
        validated_items.append({'product_id': item['product_id'], 'quantity': item['quantity'], 'price': product.price})

    # 3. Process payment
    payment_status = payment_gateway.charge(user_data.payment_token, total_amount, payment_info)
    if payment_status['status'] != 'success':
        logger.error(f"Payment failed for order {order_id}. Reason: {payment_status['message']}")
        return {"status": "error", "message": f"Payment failed: {payment_status['message']}"}

    # 4. Create order record
    order_record = {
        "order_id": order_id,
        "user_id": user_id,
        "items": validated_items,
        "total_amount": total_amount,
        "payment_ref": payment_status['ref_id'],
        "status": "pending_delivery"
    }
    db.save_order(order_record)

    # 5. Send confirmation email
    email_service.send_order_confirmation(user_data.email, order_record)

    logger.info(f"Order {order_id} processed successfully.")
    return {"status": "success", "order_id": order_id}
```

## 實戰案例：高耦合函式的解耦重構

假設我們有一個前端應用調用的 API 處理函式，它包含用戶認證、數據驗證、業務邏輯執行、數據持久化和日誌記錄等多個職責。

**原始高耦合函式範例 (JavaScript/Node.js):**

```javascript
async function handleUserRequest(req, res) {
    try {
        // 1. User authentication and authorization
        const userId = req.headers['x-user-id'];
        if (!userId || !authenticate(userId)) {
            return res.status(401).json({ message: 'Unauthorized' });
        }

        // 2. Input data validation
        const { itemId, quantity } = req.body;
        if (!itemId || quantity <= 0) {
            return res.status(400).json({ message: 'Invalid item or quantity' });
        }

        // 3. Business logic: Check inventory & calculate price
        const product = await productRepository.findById(itemId);
        if (!product || product.stock < quantity) {
            return res.status(400).json({ message: 'Product out of stock' });
        }
        const totalPrice = product.price * quantity;

        // 4. Data persistence: Update inventory & create transaction
        await productRepository.updateStock(itemId, quantity);
        await transactionRepository.create({ userId, itemId, quantity, totalPrice });

        // 5. Logging
        logger.info(`User ${userId} successfully processed item ${itemId}. Total: ${totalPrice}`);

        return res.status(200).json({ message: 'Request processed', totalPrice });

    } catch (error) {
        logger.error(`Error in handleUserRequest: ${error.message}`);
        return res.status(500).json({ message: 'Internal server error' });
    }
}
```

**使用 DeepSeek 進行解耦重構的步驟：**

1.  **初始分析請求：**
    ```
    提示詞：
    「請分析以下 JavaScript 函式 `handleUserRequest`，識別它所承擔的所有職責，並指出哪些職責應該被分離，以及為什麼。請評估其耦合度並提供初步的模塊化建議。」
    ```
    DeepSeek 會識別出認證、驗證、業務邏輯、數據持久化和日誌記錄等職責，並指出高耦合性。

2.  **模塊設計與生成：**
    ```
    提示詞：
    「基於你對 `handleUserRequest` 函式的分析，我希望將其重構為以下模塊：
    1. `AuthService` (負責認證和授權)
    2. `ValidationService` (負責輸入數據驗證)
    3. `ProductService` (包含產品庫存檢查、價格計算及庫存更新等業務邏輯)
    4. `TransactionService` (負責交易記錄的持久化)
    5. `Logger` (獨立的日誌記錄)

    請為 `AuthService`、`ValidationService` 和 `ProductService` 各自設計一個簡潔的類接口（方法簽名及簡要描述），並提供這些服務在一個新的 `handleUserRequest` 函式中協調運作的範例骨架代碼。」
    ```
    DeepSeek 會生成各個服務的類定義草稿，以及一個新的 `handleUserRequest` 函式，其中包含了對這些服務的調用。

3.  **精化重構代碼：**
    ```
    提示詞：
    「請根據上述設計，為 `ProductService` 提供完整的實現代碼，其中應包含 `findById` 和 `updateStock` 方法。假設 `productRepository` 是一個外部依賴。同時，請重寫 `handleUserRequest` 函式，使其完全使用新設計的服務來完成任務，並確保錯誤處理和日誌記錄的集成。」
    ```
    DeepSeek 將逐步生成重構後的代碼，將原始函式的複雜邏輯拆分到不同的服務中。

這個迭代過程確保了每次重構都有明確的目標，並且 DeepSeek 的輸出能夠逐步引導我們走向最終的模塊化設計。

## 提升重構效率的進階技巧

為了從 DeepSeek 獲取最佳重構建議，以下是一些進階提示詞策略：

*   **持續提供上下文：** 利用 DeepSeek 的多輪對話能力。當你在討論一個特定的代碼片段或模塊時，無需每次都重複提供所有代碼。在後續的提示詞中，只需提及「基於我們之前討論的 `OrderService`...」即可。
*   **限定輸出格式：** 要求 DeepSeek 輸出特定格式，例如 JSON、Markdown 表格、UML-like text，甚至是一個新的文件結構。
    *   `「請以 Markdown 表格形式，列出 `OrderService` 的所有公共方法、參數、返回類型及簡要說明。」`
    *   `「請以 JSON 格式，列出 `process_order_legacy` 函式所有識別出的職責及其建議的新模塊名稱。」`
*   **約束技術棧與設計模式：** 明確指出你正在使用的語言、框架（如 React, Spring Boot）、設計模式（如策略模式、工廠模式、Repository 模式），以便 DeepSeek 生成更符合實際情境的代碼。
    *   `「請以 Java Spring Boot 的 Repository 模式為基礎，為 `OrderService` 設計數據訪問層接口。」`
*   **要求測試生成：** 讓 DeepSeek 協助生成單元測試或集成測試，這是確保重構品質的關鍵一環。
    *   `「請為 `ProductService` 的 `updateStock` 方法，生成至少三個基於 Jest (JavaScript) 的單元測試用例，包括正常情況、庫存不足和產品不存在的情況。」`
*   **考慮邊界情況與錯誤處理：** 提示 DeepSeek 在設計模塊或生成代碼時，考慮異常處理、輸入驗證、併發問題等。
    *   `「在設計 `ProductService` 的接口時，請考慮庫存更新時的併發問題，並建議如何處理。」`

## DeepSeek 使用提示：安全與倫理考量

儘管 DeepSeek 是強大的工具，但在處理公司遺留代碼時，務必遵守以下原則：

*   **避免輸入敏感資訊：** 絕不將含有真實客戶數據、商業機密、私鑰或其他敏感資訊的代碼直接輸入到公共 AI 平台。務必對代碼進行抽象化、匿名化或脫敏處理。
*   **始終人工審核輸出：** DeepSeek 生成的代碼和建議可能存在「幻覺」或不完全符合特定業務邏輯的情況。將 AI 視為一位資深助理，而非最終決策者。
*   **理解其局限性：** AI 擅長模式識別和代碼生成，但對於複雜的業務背景、隱藏的業務規則或未在代碼中明確表達的意圖，仍需人類專家來判斷。
