## DeepSeek MoE 架構與顯存挑戰

DeepSeek MoE 模型透過將大型網絡分解為多個「專家網絡」（Experts），並利用一個門控網絡（Gating Network）在推理時動態選擇相關專家來處理輸入。這種設計在計算效率上優勢顯著，但在顯存管理方面卻帶來獨特挑戰：

1.  **動態專家載入：** 由於每次請求可能只啟用部分專家，模型的總參數量雖大，但實際激活的參數較少。這意味著顯存中需要儲存所有專家權重，但只有被選中的專家權重會被讀取和計算。
2.  **顯存碎片化：** 頻繁地載入與卸載專家權重，或在不同請求間切換選定專家，會導致顯存空間產生大量碎片，降低顯存利用率，甚至觸發內存不足（OOM）錯誤。
3.  **性能抖動：** 顯存分配與釋放操作（如 `cudaMalloc` 和 `cudaFree`）本身具有一定的延遲。在高峰期，這些操作可能成為推理延遲的主要來源，導致服務響應時間不穩定。
4.  **暖機時間：** 服務啟動後，首次請求需要將模型權重載入顯存，這會產生額外的延遲，影響用戶體驗。

為了解決這些問題，實現顯存分配持久化至關重要。其核心思想是，一旦模型權重或其他必要的數據結構被載入GPU顯存，就盡可能地保持其駐留，避免不必要的釋放與重新分配。

## 顯存分配持久化策略基礎

在DeepSeek MoE模型服務化部署中，顯存持久化主要圍繞以下幾個方面展開：

### 1. 模型預載入與權重常駐

最直接的持久化方法是在服務啟動時，將DeepSeek MoE模型的所有專家權重全部載入GPU顯存。即使某些專家在單次推理中不會被激活，其權重依然保留在顯存中。
*   **優點：** 消除後續推理的載入延遲，保證首次響應速度。
*   **挑戰：** 需要足夠的顯存空間來容納所有專家權重。對於超大型MoE模型，可能需要多GPU分佈式部署。

### 2. CUDA 顯存池（Memory Pool）管理

CUDA 11.2 引入了統一顯存池（`cuMemPool`），這是一項關鍵的顯存優化技術。它允許應用程式預先分配一個大塊的GPU顯存，並從中快速分配和釋放小塊顯存，而無需頻繁與驅動程序交互。
*   **適用場景：** 當DeepSeek MoE模型在推理過程中需要動態分配中間激活（activations）或其他臨時張量時，顯存池能有效減少碎片化和分配延遲。
*   **操作方法：** 可以通過 PyTorch 的 `cuda.memory.change_current_allocator` 或直接使用底層 CUDA C++ API 進行配置。

### 3. 優化推理引擎配置

許多高性能推理引擎（如 vLLM, TensorRT-LLM）已經內置了針對LLM和MoE模型的顯存管理優化。它們通常提供配置選項，允許用戶控制顯存預分配、鍵值緩存（KV Cache）策略等。

*   **KV Cache 管理：** 在生成式AI任務中，KV Cache會佔用大量顯存。合理的KV Cache分配策略（例如動態調整大小、頁面化KV Cache）對於MoE模型同樣重要，確保其不會因KV Cache導致顯存溢出。
